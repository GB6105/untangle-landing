> 요약: 확정 직후 쪼갤 카드 고르기/건너뛰기와 데모 내 쪼개기(기존 /api/split·SplitChat 로직 재사용 + 질문 상한 등 필수 소폭 수정, useSplitFlow 추출) — 데모 2단계(쪼개기) 연계를 구현할 때 읽는다.

# 쪼개기 연계

## 1. 목적

- PRD 5.2 Subtask-split을 데모 흐름에 연결한다: 오늘 할 일 확정 직후 쪼갤 일 **하나**를 고르거나 건너뛰고, 결과 서브태스크(≤5)+첫 단계를 **카드에** 확정 반영한다.
- 검증된 기존 자산(`/api/split`, `SplitChat` 대화 로직)을 최대 재사용하되, 데모 요구(카드 주입·카드 반영·**질문 상한 보장**)에 맞게 분리·소폭 수정한다.

## 2. 사용자 스토리

- 확정 직후 '지우'는 "이 중 가장 막막한 일이 있나요?"라는 물음에 카드 하나를 고르고, 짧은 문답(최대 2~3회) 끝에 5개 이하의 서브태스크와 "지금 할 첫 단계"를 받는다.
- 막막한 게 없으면 "괜찮아요, 바로 시작할게요"로 건너뛰고 Today로 간다.
- Today에서 카드가 여전히 막막하면 그 카드에서 쪼개기를 다시 시작하고, 이미 쪼갠 카드는 저장된 계획을 다시 열어 항목을 더 잘게 쪼갠다(이전 문답·완료 현황에 이어서).

## 3. 화면·인터랙션 명세

### 3.1 쪼갤 카드 고르기 (`phase: split`, `splittingCardId === null`)

- 확정 직후 같은 채팅 흐름에서 AI가 묻는다: "이 중 가장 막막한 일이 있나요? 하나만 골라주시면 같이 쪼개볼게요."
- 선택지 = 방금 확정한 카드 1~3개 칩 + **"괜찮아요, 바로 시작할게요"(건너뛰기)** 칩.
- `big === true`인 카드가 있으면 추천 문구에만 활용("OO이 가장 막막해 보여요") — 자동 선택은 하지 않는다(원칙 3). 후보 화면에서 big을 표시하지 않는 결정은 00 결정 7.
- 건너뛰기 → 곧장 `today`(04 문서). 쪼개기는 Today의 각 카드에서 언제든 시작 가능(PRD 5.2 "카드 상세에서도 언제든"의 데모 버전).
- **한 번에 하나만** 쪼갠다(PRD: "쪼갤 일 하나"). 여러 카드 연속 쪼개기 유도는 하지 않는다.
- **카드 선택 직후(숨은 대기 예고 — 필수)**: 카드를 고르면 intro 없이 즉시 초기 advance 호출이 나가므로, 첫 질문 도착 전 5~10초의 숨은 대기가 생긴다. 선택하자마자 AI 말풍선 **"좋아요. 몇 가지만 짧게 여쭤볼게요."** 를 즉시(로컬) 표시하고, 이어서 공통 대기 연출(3.2)로 잇는다 — 아무 피드백 없는 정지 화면은 최대 이탈 지점이므로 금지.

### 3.2 clarify → result (`splittingCardId !== null`)

- clarify: 필요한 맥락만 한 번에 하나씩, 옵션 칩 + 자유 입력 병행, 이미 명확한 항목은 건너뜀. goal은 카드 title을 주입 — intro(목표 입력) 단계 없음. **브레인덤프 원문을 `context`로 항상 전달한다**(§4 필수 확장) — 이미 파악된 맥락을 재질문하지 않아 질문 수가 준다(원칙 2).
- **질문 상한(목표 2회, 최대 3회) — 필수 보장 메커니즘**. 주의: 기존 `ADVANCE_SYSTEM`은 5개 맥락 키(why/current/done/capacity/blocker)가 모두 명확해질 때까지 하나씩 계속 묻는 구조로 **질문 수 상한이 없다**(코드 확인 — 최대 5회 가능). 게다가 데모는 짧은 카드 title만 goal로 주입하므로 초기 맥락이 적어 방치하면 질문이 더 많아진다. 즉 "기존 동작 유지"로는 PRD 5.2의 "최대 2~3번"이 담보되지 않으므로, 아래 3중 장치를 **필수**로 구현한다:
  1. **프롬프트 수정(필수)**: `ADVANCE_SYSTEM`에 질문 상한 지시를 추가한다 — "질문은 대화 전체에서 2회를 목표로 하고 3회를 절대 넘기지 마세요. 답변이 2개 이상 쌓였으면 남은 항목은 합리적으로 가정하고 ready로 전환하세요. 사용자가 바로 쪼개달라고 하면 즉시 남은 항목을 가정하고 ready로 전환하세요." (스킵 칩 지시까지 **한 번의 수정으로 포함** — "선택 확장"이 아니다. 스킵 칩의 확실성이 이 지시에 의존한다.)
  2. **클라이언트 소프트 가드**: 3번째 답변을 전송할 때 answer 뒤에 "(남은 건 알아서 가정하고 이대로 쪼개주세요)"를 덧붙여 ready 전환을 유도한다.
  3. **클라이언트 하드 가드**: answers가 3개인 상태에서 `need_more`가 또 오면 질문을 사용자에게 노출하지 않고, 스킵 문구를 answer로 자동 advance 1회 재호출한다(→ 지시 1이 ready 전환 보장). 그래도 `need_more`면 에러 배너("다시 시도") — **4번째 질문이 화면에 뜨는 경로는 존재하지 않는다.**
- **스킵 칩**: 매 질문의 옵션 칩에 "그냥 이대로 쪼개줘" 상시 노출. 누르면 해당 문구를 answer로 advance 호출(지시 1이 즉시 ready 전환을 보장).
- **대기 연출(advance·resplit 공통 — 05 §4.2 횡단 방침)**: 모든 LLM 대기에 02 §3.1과 같은 마이크로카피 순환(2.5초 간격) + 8초 초과 안내를 적용한다. 기존 `SplitChat`의 바운스 점 3개만 두는 것은 금지. 쪼개기용 카피 예: "이 일을 찬찬히 살펴보는 중…" → "작은 단계로 나누는 중…" → "거의 다 됐어요". `useSplitFlow`/`DemoSplitPanel` 공통 명세.
- result: **서브태스크 ≤5 + 지금 할 첫 단계 1개**(기존 스타일 재사용). 항목별 "더 잘게" 재분해(기존 resplit — 확정 전 대체는 result 영역 안에서만).
- **result의 선택 컨트롤은 Today의 완료 체크박스와 다른 시각 형태로 한다**(포함/제외 칩 토글 등): result의 선택은 "카드에 담을 항목 고르기", Today의 체크는 "완료"다. 같은 체크박스를 쓰면 확정 직후 전부 해제된 동일 목록을 만나 "내 선택이 날아갔다"고 오독한다(04 §3.2와 쌍).
- **5개 상한 규칙**: resplit는 새 하위 항목(≤5)+나머지 기존 항목을 합쳐 목록이 5개를 넘을 수 있다(기존 동작 — 최대 9개 표시). 그러나 **확정은 항상 최대 5개 선택**으로 제약한다: resplit 후 합산 목록이 5개를 넘으면 기본 선택을 새 하위 항목 우선으로 5개까지만 유지하고, 사용자가 5개를 초과해 선택하면 확정 버튼 비활성 + "오늘 카드에는 5개까지만 담을 수 있어요" 안내. (§5의 불변식 `subtasks ≤ 5`를 UI에서 보장 — PRD "서브 테스크 5개 이하")
- **확정**: 담을 서브태스크를 선택 컨트롤로 고르고(기본 전체 선택 — 5개 초과 시 위 규칙, 최소 1개) **"이 계획으로 시작"** 버튼 → 카드에 반영. 확정 전 카드에는 아무것도 붙지 않는다(원칙 3).
- 확정 후: "다른 카드도 쪼갤까요?"라고 **묻지 않는다**(질문 최소화 + 압도 방지). 바로 `today`로 전이. 나머지 카드에서 쪼갤 수 있음은 Today의 카드 UI로만 암시.

### 3.3 Today에서의 재진입

- **미분해 카드의 "쪼개기"**: `split` phase 재진입(`splittingCardId` 세팅) — goal = 카드 title, answers = 빈 배열로 3.2의 clarify부터 시작(첫 쪼개기와 동일. 3.1의 즉시 안내 문장도 동일 적용).
- **쪼갠 카드의 "더 쪼개기"**: clarify를 다시 돌지 않는다. 저장된 `subtasks`·`firstStep`으로 **result 화면을 재구성**하고, **항목별 resplit만 허용**한다. advance 재호출은 하지 않는다 — 기존 서브태스크를 모르는 채 전체를 새로 분해해 돌려주기 때문(API 액션 수준에서 확정).
  - resplit 요청은 기존 계약 그대로: `answers = 저장된 splitAnswers`(**이전 문답에 이어감** — PRD 5.2, 원칙 4), `taskToSplit = 선택 항목 title`, `otherTasks = 나머지 항목 title들`.
  - **완료 현황 전달(계약 변경 없음)**: 완료된 서브태스크는 `otherTasks` 문자열에 "(완료)" 접미사를 붙여 보낸다(예: "자료 조사하기 (완료)") — `string[]` 계약 안에서의 클라이언트 표기 컨벤션이며 신규 필드를 만들지 않는다(§7 제외 목록과 정합). 완료된 항목은 `taskToSplit`으로 선택할 수 없다(이미 끝난 일을 더 쪼갤 이유가 없음).
  - 재확정 시 카드의 `subtasks`를 새 선택으로 대체하되, 제목이 유지된 기존 항목의 `done` 상태는 보존한다.

## 4. 엔지니어링: 재사용 전략

- **소폭 수정 재사용 — `app/api/split/route.ts`** (00 §7과 동일 분류. "무수정 재사용"이 아니다):
  - 계약의 액션 구조·응답 스키마(advance/resplit)는 그대로. goal = 카드 title, answers = 해당 카드의 clarify 히스토리. **필수 수정은 두 가지뿐**:
    1. `ADVANCE_SYSTEM` 질문 상한·잔여 가정·스킵 지시(3.2-1).
    2. advance 요청에 `context?: string`(브레인덤프 원문) 추가 → 프롬프트에 `[오늘의 맥락]` 블록으로 전달. **필수 채택** — 데모는 항상 담아 보낸다. 질문 수 감소(원칙 2)와 00 §2 시간 예산의 전제. 필드가 없으면 기존 동작과 동일한 하위 호환 확장이다.
  - 완료 현황은 3.3의 `otherTasks` "(완료)" 표기 컨벤션으로 전달 — 필드 추가 없음.
- **무수정 재사용**: `ChatBubble`, `OptionChips`, `TaskCard`.
- **`useSplitFlow` 훅 추출** (`components/split/useSplitFlow.ts`): `SplitChat`은 대화 로직 + 랜딩 전용 UI(내 할 일 목록, `untangle:todos` 저장)가 결합돼 있어 분리한다. 데모와 어긋나는 4가지: (a) intro에서 goal 직접 입력 ↔ 데모는 title 주입 후 즉시 clarify, (b) flat `untangle:todos` 저장 ↔ 데모는 카드의 `subtasks` 반영, (c) "내 할 일" 목록 렌더 불필요, (d) reset 대신 "Today로 돌아가기".

```ts
type UseSplitFlowArgs = {
  provider?: Provider;            // 데모는 claude 고정
  goal: string;                   // 카드 title 주입
  initialAnswers?: Answer[];      // 다시 쪼개기: 이전 문답 이어가기
  initialResult?: { tasks: Task[]; firstStep: Task }; // 쪼갠 카드 재진입: result 화면 재구성(3.3)
  context?: string;               // 브레인덤프 원문 — 데모는 항상 전달(§4 필수 확장)
  onConfirm(result: { tasks: Task[]; firstStep: Task; answers: Answer[] }): void;
};
// 반환: log/pending/tasks/firstStep/checked/error/retry/loading 상태와
// runAdvance·answerPending·runResplit 액션, gen-ref 스테일 가드,
// 질문 상한 소프트/하드 가드(3.2-2·3)와 선택 5개 상한(3.2) 포함.
```

- 소비자는 데모의 `DemoSplitPanel` 하나(Experience 진입점화로 인라인 `SplitChat` 소비처가 사라짐). 인라인 유지로 결정이 바뀌어도 두 소비자가 같은 훅을 쓰는 구조가 성립.
- **주의**: `origin/feat/split-analytics`가 `SplitChat.tsx`를 수정한다 — 훅 추출 전에 그 브랜치의 머지/폐기를 정리할 것(05 문서).

## 5. 상태·데이터

- 전이: `candidates --(확정)--> split(고르기)` → [카드 선택] `split(clarify/result)` → [확정 or 뒤로] `today`; `today --(미분해 카드 쪼개기)--> split(clarify)` / `today --(쪼갠 카드 더 쪼개기)--> split(result 재구성)` 재진입(3.3).
- 확정 시 카드 갱신: `subtasks = 선택된 항목(≤5 — 3.2의 선택 상한으로 UI에서 보장, 신규 항목 done: false, 재확정 시 유지 항목의 done 보존)`, `firstStep = { title, done: false }`, `splitAnswers = answers` 저장. resplit 결과도 확정 시에만 대체.
- clarify 대화 로그는 저장하지 않음(00 §5) — 복원 시 `splitAnswers` 기반으로 이어간다.

## 6. 엣지 케이스

- clarify 도중 이탈 후 재진입: 답변 중이던 미완 문답은 유실 허용(결과물이 아직 없음 — 00 §6 원칙 4의 보존 범위) — `splittingCardId`와 기존 `splitAnswers`로 고르기 화면부터 재개.
- 하드 가드(3.2-3)의 자동 스킵 advance마저 `need_more` 반환: 에러 배너 + "다시 시도"(같은 자동 스킵 호출 재실행). 추가 질문 노출은 없다.
- resplit 진행 중 확정 버튼: 비활성(기존 `resplittingId` 패턴).
- API 에러·네트워크: 기존 배너 + "다시 시도"(마지막 요청 재실행), gen-ref로 스테일 응답 무시.
- 서브태스크 전체 해제: 확정 버튼 비활성(최소 1개). 5개 초과 선택: 확정 버튼 비활성 + "오늘 카드에는 5개까지만 담을 수 있어요"(3.2).
- 세 카드를 모두 쪼개고 싶은 사용자: Today에서 카드별로 재진입하면 가능 — 흐름상 유도만 하지 않는다.

## 7. 구현 범위

- **포함**: 쪼갤 카드 고르기 화면(+선택 직후 즉시 안내 문장), `useSplitFlow` 추출(질문 상한 소프트/하드 가드 포함), `DemoSplitPanel`(clarify·result·확정·공통 대기 연출), 스킵 칩, **`ADVANCE_SYSTEM` 질문 상한·가정·스킵 지시 수정(필수)**, **advance `context` 확장(필수)**, 완료 현황 `otherTasks` 표기 컨벤션, Today 재진입 연결(미분해 = clarify, 쪼갠 카드 = result 재구성 + 항목별 resplit).
- **제외**: 위 두 가지 필수 수정(§4) 외 `/api/split` 계약 변경 — 완료 현황용 신규 필드도 만들지 않는다(`otherTasks` 표기로 갈음). 여러 카드 동시 쪼개기, 쪼개기 결과 편집(부가 기능).

- 04(Today)가 이 문서의 재진입 동선과 카드 갱신 결과를 소비한다.
